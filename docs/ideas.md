## 一、语音

### 1. 本地语音识别 ★★★

> 已做，见决策 0027（选 A，模型打进安装包）。

现在语音要上传给百炼的 qwen3-asr-flash：没网不能用，而且 2026-11-07 实测里语音识别比整理还慢。
用户以前用过一个 200 多 MB、效果不错的本地模型。体积对得上的是 SenseVoice-Small 的 int8 版（239 MB，
`csukuangfj/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`），中文好、自带标点，而且不是逐字生成，速度快。

| 备选                                                                                                   | 取舍                                                                                                                  |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| **A sherpa-onnx（Apache-2.0，有现成的安卓库）+ SenseVoice-Small，写一个 Capacitor 插件在安卓原生层跑** | 速度最好，用手机 CPU 原生跑；要写一点 Kotlin/Java；只有安卓 App 能用                                                  |
| B 同样的模型，在 WebView 里用 WebAssembly 跑                                                           | 网页版也能用；但 239 MB 要整个读进 wasm 内存，手机上可能吃不消；网页版托管要切成 10 块以上（Cloudflare 单文件 25 MB） |
| C Whisper-small，用现成的 transformers.js（int8 约 250 MB）                                            | 和语义搜索共用一套推理库，接入最省事；但中文不如 SenseVoice，常出繁体、缺标点，而且是逐字生成，手机上慢               |
| D 继续只用云端                                                                                         | 不用改；没网不能录、慢的问题还在                                                                                      |

推荐 A，策略是"App 里本地优先，识别失败或网页版时用云端"。好处：快（不用上传音频）、没网也能用、声音不离开手机。

要注意：SenseVoice 的模型权重用的是 FunASR 自己的模型协议，不是 MIT/Apache。开源前要读一遍条款；
稳妥的做法是不打包进仓库和安装包，第一次用时从 ModelScope 或 Hugging Face 下载（国内 ModelScope 可达）。

### 2. 语音里的心情和声音事件 ★★

SenseVoice 模型本身能识别情绪（开心、伤心、生气……）和声音事件（笑声、掌声、音乐）。
可以作为"心情"标签的候选，用户点了才加；回顾页可以统计"开心的记录多在哪些地方"。
情绪识别不准，只能当建议。sherpa-onnx 里能不能拿到这两项要实测。

### 3. 长语音和自动分段 ★

边走边说一两分钟时，用语音活动检测（sherpa-onnx 自带 Silero VAD）切成几段再识别，不用一直按着按钮。

## 二、LLM 调用本身的工程（花费小、收益明显）

### 1. 结构化输出，代替"从回复文本里找 JSON" ★★★（已做，0016）

现在 `server/dashscope.ts` 的 `extractJsonObject` 在回复里找第一个 `{` 到最后一个 `}`，解析失败就返回 502，用户只能重试。
改成让模型按格式输出（JSON 模式或函数调用），用 zod 自带的 JSON Schema 导出，一份结构同时约束模型和校验结果；
校验失败时把错误原因发回模型自动修一次。要先查百炼文档，确认 qwen3-vl-plus 支持哪一种。

### 2. 按任务选模型 ★★★（已做，0016）

偏好提炼、出行总结、没有照片的"只补标题"现在都用看图的 qwen3-vl-plus。纯文字的任务换成更快、更便宜的文字模型，
有照片才用看图模型。改动只在服务端几行。

### 3. 用量和费用记账 ★★（已做，0016）

百炼每次返回用了多少 token。服务端把它带回前端，本机记下来，偏好页显示"这个月用了多少、大约多少钱"。
也能用来定第四档限流的阈值。

### 4. 边生成边显示（流式输出） ★★

一直挂着的待定项。等手机上的"整理用时"数据：模型生成占大头才值得做。

### 5. 忠实度检查，并从修改里学"不要用的词" ★★★（已做，0016）

直接针对最早的"太搞"问题：

- 生成后自动检查：正文里出现了原话里没有的数字、价格、人名，就标出来或自动重写一次。
- 从修改记录里统计用户反复删掉的词（比如"热气腾腾""治愈"），自动加进提示词"不要用这些词"，并在生成后检查。

这是一个"从用户反馈自动学规则"的闭环，规则看得见、可以删，比只靠例子稳定。

### 6. 例子按相似度挑 ★★

决策 0012 的少样本例子现在取最近 2 次修改。语义搜索的向量已经有了，可以改成挑和这条记录最像的修改
（同类别、内容相近）。写探店时参考的是以前改探店的例子，不是刚改过的风景。

### 7. 选哪几张照片给模型 ★★

现在总是按顺序发前 4 张。先用便宜的办法：模糊检测（拉普拉斯方差）去掉糊的，感知哈希去掉连拍的重复，
剩下的挑差别最大的 4 张。不用模型，几十行代码。分享图的封面也用同一套。

### 8. 追问模式 ★★

原话很短时，模型先问一句（"你点了什么？"），用户用语音回答，再写正文。
事实来自用户，不靠模型编，正好解决"添油加醋"。遇见集也有追问。最多问一次，可以跳过。

## 三、RAG（检索增强生成）

### 1. "问问我的足迹" ★★★

用自然语言问自己的记录："去年在杭州吃过哪些面？""第一次去上海是哪天？"

| 备选                                                                                                               | 取舍                                                   |
| ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| **A 在手机上检索（筛选条件 + 字面匹配 + 现有向量），只把检索到的几条记录的文字发给模型作答，答案里带可点开的记录** | 保持本地优先，只发相关的几条；向量索引 3A 已经有了     |
| B 把全部记录传到服务端的向量数据库                                                                                 | 违反 0002（服务端不存用户数据）                        |
| C 不检索，把全部记录塞进上下文                                                                                     | 记录少时最简单，可以当对照组；记录多了贵、慢，还会漏看 |

建议 A，并且拿 C 做对照实验：记录多到多少条时检索开始比"全塞进去"更好。这是一个能讲清楚的工程问题。
配一套 20 个左右的问题和标准答案（应该找到哪几条），算检索召回率和答案正确率。
"去了几次""哪个月最多"这类统计问题，检索不擅长，交给第四节第 2 点的工具。

### 2. 写新记录时参考"上次在这里写的" ★★

第 3 次来同一家店时，把上次的原话一起给模型，可以写出"上次点了 X，这次换了 Y"。
只用用户自己的话，不引入外部知识，不会编。

### 3. 照片也能按内容搜 ★

用中文 CLIP 一类的图文模型给照片算向量，搜"海边""猫""夜景"能找到没写过这些字的记录；顺带用于照片去重和挑封面。
模型几百 MB，手机上的速度要实测。

### 4. 向量存储先不上专门的库（工程判断）

一条向量 512 维、2 KB，一万条才 20 MB，全部扫一遍在手机上也就几十毫秒。
记录到上万条之前不引入近似最近邻索引（HNSW、sqlite-vec），省掉一层复杂度。把这个阈值写下来，到了再换。

## 四、Agent

### 1. 定位 Agent（缩小版的 geo-sleuth） ★★★

给没有定位的记录找地点。模型可以调用这些工具：

- 查照片线索（电话、车牌查表）
- 在某个城市里按名字查地点
- 当天去过的地方
- 附近以前去过的地方
- 问用户一个问题

最多调用 5 次左右，最后给出候选地点和证据（"电话区号 0571 → 杭州；同一天 14:00 在西湖"），用户点了才写入。
沿用 geo-sleuth 的规则：每个结论都要对应一次真实的工具结果。范围小、能验证、直接有用。

### 2. "问问我的足迹"做成带工具的 Agent ★★★

和第三节第 1 点是同一个功能，只是架构不同：检索只是其中一个工具，另外还有：

- 统计去过几次
- 按条件列出记录
- 某段时间的统计

**工具在手机上执行，直接查本地数据库；服务端仍然只转发消息，不存数据。**
界面上显示它查了什么（"查了：杭州 · 美食 · 2025 年"），和 geo-sleuth 一样把过程摆出来。
建议先做检索工具（第三节第 1 点就是它的子集），再加统计工具。

### 3. 主动发现出行 ★★

打开 App 时扫描相册里新增的照片，按时间和地点分组（复用出行归组规则），提示"昨天在西湖拍了 23 张，要记一条吗？"，
照片已经挑好。在用户点之前什么都不上传。最贴近"懒得整理"这个初衷，但要写原生插件读相册，
并申请读取照片和照片位置的权限（Android 13 起是 `READ_MEDIA_IMAGES`，读 GPS 还要 `ACCESS_MEDIA_LOCATION`）。

### 4. Agent 的安全约束（做第 1–3 点时一起定）

- 照片里招牌、海报上的字可能写着"忽略之前的指令……"（提示词注入）。工具结果一律当数据，不当指令。
- 工具默认只读；任何会改记录的操作都要用户确认。
- 限制步数和 token 数，防止死循环烧钱。

### 5. Agent 的评估和运行记录 ★★

本机保存每次运行的步骤（调用了什么、结果、耗时）。配一套任务集，统计成功率、平均调用次数、耗时，
改提示词或工具后跑一遍对比。和第四档的提示词样例集合在一起做。

## 五、端侧模型（体积不限之后才可能）

### 1. 本地 OCR ★★

PaddleOCR 的手机版模型转 ONNX 只有十几 MB。没网时也能读出照片里的电话、招牌，给查表和定位 Agent 用；
照片里的字（菜单、门牌）也能被搜索到。

### 2. 本地小语言模型 ★

用 0.5B–1.5B 的 Qwen 量化版（约 0.4–1 GB），没网时先补标题、类别、标签，联网后可选用云端重写。
看图和写正文质量不够。安卓上要走原生（llama.cpp 一类）；WebView 里的 WebGPU 支持情况要实测。

## 六、工程质量（非 AI）

### 1. 边界数据挪出主线程，并缩小文件 ★★★（已做，0016）

第三档的 `backfillGeo` 在主线程解析 9.7 MB 的 JSON 并逐个判断多边形，手机上可能卡顿一下；
离线底图一次画 4586 个多边形也重。改成在 Web Worker 里做，数据换成共享边界的 TopoJSON 或二进制格式（预计能小好几倍）。
这是第三档留下的债。

### 2. 持久化的后台任务队列 ★★★

> 已做简化版：只排 AI 整理，见决策 0027 第 4 条。

AI 整理、地名查询、向量、区域补算都放进 IndexedDB 里的任务队列：失败自动重试、隔一段时间再试、联网后继续。
现在保存时没网就不整理，失败要手动点重试。配合本地语音，就能做到"没网时照样记，有网了自动整理"。

### 3. 前后端类型自动对齐 ★★

用 Hono 自带的 RPC 客户端（`hc<AppType>`）代替手写的 fetch。接口的路径、参数、返回类型直接从服务端推出来，改接口时前端立刻报错。

### 4. 多设备同步：端到端加密备份到自己的网盘 ★★

继续本地优先，用用户自己的口令加密后，同步到 WebDAV（坚果云支持）等网盘；服务端仍然不碰数据。
前提是第 5 点。工程量较大，但解决"换手机、手机丢了"的根本问题。

### 5. 记录加修改时间和删除标记 ★★

现在记录没有 `updatedAt`，删除就是真删。同步和备份合并都需要知道"哪个版本更新""哪条被删过"。改动小，越早加越好。

### 6. 安全加固 ★★

- 现在所有设备共用一个口令：改成每台设备一个、可以单独吊销（存在 Cloudflare KV）。
- 加安全响应头（CSP）。
- CI 里跑依赖漏洞扫描。

### 7. 分享图截图对比测试 ★

把五种版式渲染出来和基准图逐像素比较，排版一改坏就知道。和第四档的界面测试一起做。

### 8. 体积预算检查 ★

首屏代码现在 457 KB，之前定的上限是 500 KB。CI 里加检查，超了就失败。

### 9. 自己的使用数据看板 ★★★

只在本机统计：每周打开几次、记几条、语音和文字各占多少、AI 正文的改动比例怎么变化（学习有没有效）、
整理耗时的分布（已经在记）。最早的计划里就要"连续用两周，记下实际打开了几次"来检验留存假设，现在没有数据。
可以导出 CSV 自己分析。

## 七、产品

1. 学习分享版式偏好 ★：记下每次选了哪种版式，下次自动推荐时参考。
2. 年度报告 ★★：先让模型写每个月的总结，再由月度总结写年度（分层总结），比一次塞进全年的记录更稳。
3. 照片挑封面、去重、去糊：见第二节第 7 点。
4. 心情统计：见第一节第 2 点。

## 不推荐

- ✗ 用百科或地点资料给正文"补充知识"：和 0012 定的"只写用户说的和照片里有的"冲突，正是"太搞"的来源。
- ✗ 把记录同步到自己的服务器做向量库或推荐：违反 0002。
- ✗ 现在就上向量数据库或 LangChain 这类框架：数据量和流程都还用不上，徒增依赖。
