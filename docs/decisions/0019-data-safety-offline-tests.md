## 1. 安卓 App 每周自动备份（0015 的 A）

- 什么时候备份：打开 App 8 秒后检查，距上次备份（手动导出或自动备份）满 7 天、并且有记录，就在后台备份。
- 存到哪：手机的"下载/足迹手账"文件夹，文件名"足迹手账自动备份-日期-时间.zip"。只留最近 2 份自动备份，手动导出的不动。
- 怎么存：新写的原生插件 `BackupSaverPlugin.java`，用安卓 10 起的媒体库接口，不需要存储权限。
  - 只能复制 App 缓存目录里的文件。
  - 写完之前文件标记为"待定"，文件管理器里看不到半个文件。
- 失败了不算备份过：把"上次备份时间"改回去，下次打开再试。结果显示在备份页。
- 备份页（只在 App 里显示）：
  - 开关；
  - 上次自动备份的时间、大小，或者失败原因；
  - "现在备份到手机文件夹"按钮。换手机、卸载重装前用。
- 成功后在首页提一句"已自动备份到……"。
- 局限：
  - 安卓 10 以下不支持，备份页显示原因。
  - 卸载重装后，新装的 App 看不到也删不掉以前的自动备份。这些文件会一直留着，需要时自己去文件夹里删。

## 2. 备份文件不再整个放进内存（0015 推荐用 fflate 流式压缩；改成自己写"只存不压"的 zip）

**原来的问题**：

- 导出：把所有照片读成字节，再用 fflate 一次打包。内存里同时有全部照片和整个压缩包，约 2 倍备份大小。
- 导入：先把整个文件读进内存，再全部解开，又是约 2 倍。

**现在**（`src/lib/zipStore.ts`）：

- **导出**：
  - 每张照片只读一遍，算校验码（CRC-32，每次读 4 MB）；
  - zip 直接由照片原来的 Blob 拼起来，浏览器不用把照片复制到 JS 内存。
- **导入**：
  - 先读文件末尾的目录，再按位置切出每个文件；
  - 照片是原文件的切片，写进数据库时浏览器再一张张复制。
- **App 里存文件**：原来把整个备份转成一个 base64 大字符串，现在每次只转 3 MB，分块写进缓存目录（`writeCacheFile`）。

**为什么不用 fflate 的流式压缩**：

- 它也要把每张照片读成字节再交给它，输出的字节块还要另外拼起来。
- 读取时它的流式解压不好处理"大小写在文件后面"的条目。
- 备份里几乎全是 JPEG，本来就不压缩。所以自己写"只存不压"的 zip 更简单，导入时还能直接切片。

**兼容**（都有测试）：

- 新备份是标准 zip：旧版 App（fflate 的 `unzipSync`）能导入；
- 旧版 App 导出的备份，新版能导入；
- 别的工具重新压缩过的条目，读的时候会解压。

**局限**：

- 不支持 zip64：单个备份不能超过 4 GB、文件数不能超过 65535，超了会提示。
- 导入时不核对校验码：核对要把每张照片都读一遍。

**实测**（电脑浏览器，50 张照片、备份 28.6 MB）：

| 步骤 | 耗时    | 内存峰值 |
| ---- | ------- | -------- |
| 导出 | 0.12 秒 | 35 MB    |
| 导入 | 0.05 秒 | 35 MB    |

导入后照片逐字节一致。

## 3. 一次选很多大图（0015 的 A：先测再改）

在电脑浏览器里生成 50 张 4000×3000 的 JPEG（共 63 MB），走一遍导入：

| 结果         | 数值                     |
| ------------ | ------------------------ |
| 总耗时       | 4.4 秒（每张约 90 毫秒） |
| JS 内存峰值  | 17 MB                    |
| 界面最长卡顿 | 155 毫秒                 |
| 失败         | 0 张                     |

- 原来就是一张一张处理，内存没问题，不用改。
- 但手机大概慢 5–10 倍，50 张要半分钟左右，原来只显示"保存中…"。
  所以加了进度："正在处理照片 12/50…"（`importPhotos` 的 `onProgress`）。
- 还要你在手机上用真实照片测一次。真实照片比生成的图大（3–6 MB），解码更慢。

## 4. 网页版离线和"添加到主屏幕"（0015 的 A：vite-plugin-pwa 2.0.0）

- 提前缓存页面代码、样式、字体、图标，共 39 个文件，约 2 MB。第一次打开后，没网也能打开。
- 模型、运行库、边界数据、查表数据不提前下载，用到时才缓存，策略是"先走网络，没网再用缓存"：
  - 这些文件的网址不变、内容会随版本更新，"先用缓存"会一直用旧的；
  - 有浏览器缓存时，走网络只是一次很小的确认。
- `/api` 不缓存。
- 应用清单：名称、底色、图标三张（192、512、安卓的可遮罩 512）。iPhone 用的 `apple-touch-icon` 加在 `index.html`。图标都由 `scripts/make_icons.py` 生成。
- 新版本自动生效：`autoUpdate`，下次打开就是新版，不弹窗。
- 安卓 App（`--mode app`）和开发时都不启用。App 的页面本来就打包在本地，再套一层缓存只会添乱。

**实测**：

- 生产构建在浏览器里打开一次后，停掉服务器再刷新：页面、按钮、像素字体都正常，接口按预期连不上。
- 测完删掉了这个浏览器里的离线缓存。

## 5. 无障碍（0015 的 A：先在电脑上过一遍）

**发现并改了的**：

- **"＋ 选照片"和"从备份导入"读屏和键盘都用不了**：它们是 `<label>` 包着 `hidden` 的文件输入框，
  `hidden` 会让输入框完全不可聚焦，TalkBack 只能当成一段文字。
  - 改成视觉上隐藏、仍可聚焦（`sr-only`）；
  - 键盘聚焦时在按钮上画虚线框（`index.css` 的 `label:has(> input.sr-only:focus-visible)`）。
  - 实测按 Tab 能走到，名字是"＋ 选照片"。
- **分享图预览**：
  - 补上 `role="dialog"` 和名称；
  - 按 Esc 能关。
- **首页和备份页的结果提示**（"已保存 2 张""已导出……"）：加 `role="status"`，读屏会念出来。

**检查过、没问题的**：

- 五个页签和编辑页，用脚本找没有名称、或者名称只有符号的可点元素：没有。
- 图片都有 alt：装饰性的写空，分享图预览有名字。

还要你用 TalkBack 在手机上走一遍主流程。

## 8. 提示词样例对比（0015 推荐你挑 10–20 条放进不进 git 的目录；改成直接从备份里取）

`scripts/eval_prompts.ts`：

```
npm run eval -- run <备份.zip> <这次的名字> [--limit 10]
npm run eval -- report <名字A> <名字B>
```

- **样例从哪来**：直接用你从手机导出的备份。
  - 每条记录的照片、原话、地名、时间照原样发给"整理"接口，偏好说明也带上；
  - 你最后改成的版本当参考答案。
  - 比单独挑素材省事，参考答案也是现成的。
- **挑哪些**：`evals/samples.txt` 里每行一个记录 id；没有这个文件，就优先挑你改过 AI 稿子的、最近的记录。
- **怎么调用**：在本机直接调服务端代码（不用另开服务），用 `.env` 里的 key。照片用 sharp 缩到 768 像素，和 App 一样。
  sharp 原来就随 transformers.js 装在 node_modules 里，这次只是写进 devDependencies，没有新下载。
- **对比网页**：四列并排：照片和原话、你改成的、A、B。每格标出字数、耗时、token 和"可能编的"内容（复用 `faithful.ts`）。
  顶部有汇总：平均字数、带"可能编的"内容的条数、平均耗时、估算花费、用到的模型。
- **输出位置**：都在 `evals/`，不进 git，里面有你的照片和原话。
- 不让模型打分（0015 的 B）：像不像你，还得你自己看。
