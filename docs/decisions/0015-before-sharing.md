# 0015 第四档：给别人用或开源之前

- 状态：待确认（2026-11-23）。每一点列出全部备选，标"推荐"的是建议，等用户定。

## 背景

待办清单第四档（`docs/backlog.md`）：安装包还是调试版、没有开源协议、服务端没有限流、没有自动检查和界面测试、
改提示词全凭感觉、备份全靠手动、大批量导入没测过、网页版不能离线、大陆网络和读屏没实测。
第一到第三档都只在自己手机上用，这些问题不急；一旦给朋友装、或者公开仓库，就都会暴露出来。

## 分阶段和顺序（推荐）

| 阶段 | 内容                               | 排在这里的原因                                                         |
| ---- | ---------------------------------- | ---------------------------------------------------------------------- |
| 4A   | 正式签名、版本号、图标             | 换签名必须卸载重装，越早换越好；顺便部署并打包，把第三档一起拿上手机测 |
| 4B   | 开源协议、隐私说明、服务端限流     | 公开仓库或把口令给别人之前必须有                                       |
| 4C   | 自动备份、分块压缩、大批量导入实测 | 数据只在手机里，记录越多越要紧                                         |
| 4D   | 网页版离线、无障碍                 | 给 iPhone 朋友用网页版时才需要；无障碍先做能在电脑上做的部分           |
| 4E   | 界面冒烟测试、提示词样例集、CI     | 工程化，便于以后放心改；样例集要你提供素材，CI 要先建远程仓库          |

只能由用户做的：阿里云费用预警、建 GitHub 远程仓库、在大陆网络下实测、用 TalkBack 走一遍、挑提示词样例。

## 4A 安装包正式化

### 1. 签名（推荐 A）

| 备选                                                                                                            | 取舍                                                         |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **A 用 keytool 在本机生成正式密钥，放在仓库外；口令写在不进 git 的 `android/keystore.properties`，Gradle 读取** | 一条命令就能打出正式版；密钥不会被提交                       |
| B 用 Android Studio 的向导生成并签名                                                                            | 结果一样，但每次打包都要手动点向导                           |
| C 继续用调试签名                                                                                                | 调试密钥在每台电脑上不一样，换电脑打的包装不上；不能发给别人 |

**注意：从调试签名换成正式签名，手机上必须先卸载旧版再装，App 里的数据（IndexedDB）会跟着清空。**
换之前一定要先在旧版里导出备份，装好新版再导入。密钥文件和口令要另外备份，丢了以后就再也发不了能覆盖安装的更新。

### 2. 版本号（推荐 A）

| 备选                                                                                         | 取舍                                       |
| -------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **A 以 `package.json` 的 version 为准，Gradle 读取；versionCode = 主×10000 + 次×100 + 修订** | 只改一处；App 里"关于"也能显示同一个版本号 |
| B 手动改 `build.gradle`                                                                      | 容易忘，两处不一致                         |
| C 用 git 提交次数当 versionCode                                                              | 自动递增，但版本号和功能对不上             |

### 3. 图标（推荐 A）

| 备选                                                                                                 | 取舍                                       |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **A 我画一个像素风 SVG（脚印 + 星星，马卡龙配色），用 `@capacitor/assets` 生成安卓各尺寸和网页图标** | 一次生成全部尺寸；要装一个开发依赖         |
| B 用 Android Studio 的 Image Asset 向导                                                              | 不用装东西，但要你手动操作，网页图标另外做 |
| C 你自己画或找设计                                                                                   | 最合心意，但要你花时间                     |

## 4B 协议、隐私、限流

### 1. 开源协议（推荐 A）

| 备选         | 取舍                                          |
| ------------ | --------------------------------------------- |
| **A MIT**    | 0005 里的默认；最宽松，别人拿去改了也不用开源 |
| B Apache-2.0 | 多一条专利授权条款，更正式，但文本长          |
| C GPL-3.0    | 别人改了发布必须开源；会让一些人不敢用        |

同时加 `THIRD_PARTY.md`，列出打包进 App 的第三方数据、模型、字体及其协议
（Natural Earth、geoBoundaries、bge-small-zh、Fusion Pixel、geo-sleuth 的查表数据等），两份 CC BY-SA 的数据单独说明。

### 2. 隐私说明（README 里一段）

写清楚：照片和记录只存在手机里；整理时照片缩小后发给模型，服务端不保存；出行总结只发文字；
地名查询会把坐标发给 OpenStreetMap 的 Nominatim；语义搜索完全在本机；访问口令存在本机。不需要选，只是写下来。

### 3. 服务端限流（推荐 A）

| 备选                                                                                                                         | 取舍                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **A Worker 自带的限流绑定（Rate Limiting API）：按"IP + 接口"计数，AI 接口每 60 秒 20 次、地名每 60 秒 30 次，超了返回 429** | 免费、几行代码；文档说明它是近似计数、每个机房各算各的，挡得住口令泄露后的刷量，挡不住慢慢地用 |
| B Cloudflare 防火墙（WAF）的限流规则                                                                                         | 不用改代码，但规则作用在自己的域名上，`*.workers.dev` 用不了                                   |
| C 用 KV 或 Durable Object 记"每天最多多少次"                                                                                 | 能做真正的每日上限，但工程量大；KV 免费额度每天只能写 1000 次                                  |

不管选哪种，阿里云控制台的费用预警都要你自己设，这是最后一道防线。

## 4C 数据安全

### 1. 自动备份（推荐 A）

| 备选                                                                                                         | 取舍                                                                                         |
| ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| **A 打开 App 时检查：距上次备份超过 7 天，就在后台生成备份，存进手机的"下载/足迹手账"文件夹；只留最近 2 份** | 卸载 App、换手机都还在；照片多时每份可能几百 MB，所以只留 2 份；要写一个类似"存相册"的小插件 |
| B 存到 App 自己的目录                                                                                        | 不用写原生代码，但卸载就一起没了，起不到备份作用                                             |
| C 用安卓的 WorkManager 在后台定时备份，App 不打开也会做                                                      | 最省心，但要在原生代码里读网页的数据库，复杂很多                                             |

只在安卓 App 里做；网页版继续用现在的备份提醒。

### 2. 压缩改分块（推荐 A）

| 备选                                                               | 取舍                                                                 |
| ------------------------------------------------------------------ | -------------------------------------------------------------------- |
| **A 用 fflate 的流式压缩，一张照片一张照片地写，最后拼成一个文件** | 内存峰值从"整个压缩包"降到"一张照片"；文件格式不变，旧备份照样能导入 |
| B 拆成多个压缩包                                                   | 导入时要一次选好几个文件，容易漏                                     |

### 3. 大批量导入（推荐 A）

**A** 我先在电脑浏览器里生成 50 张 4000×3000 的大图走一遍导入，记下时间和内存；卡顿就改成一张一张处理并显示进度。
然后你在手机上用真实照片再测一次。**B** 直接改成逐张处理加进度条，不先测：可能白改。

## 4D 网页版离线和无障碍

### 1. 网页版离线（推荐 A）

| 备选                                                                                          | 取舍                                                       |
| --------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **A 用 vite-plugin-pwa 生成应用清单和离线缓存：页面代码提前缓存；模型和边界数据用到时再缓存** | 成熟，和 Vite 配合好；50 MB 的大文件不提前下载，不浪费流量 |
| B 自己手写离线缓存（Service Worker）                                                          | 完全可控，但更新逻辑容易写错，导致用户一直看旧版           |
| C 不做                                                                                        | iPhone 朋友没网时打不开，也不能"添加到主屏幕"              |

安卓 App 本身就离线可用，不受影响。

### 2. 无障碍（推荐 A）

**A** 我先用浏览器的无障碍信息把所有按钮、输入框、图片过一遍，补上缺的名称（比如只有"×""←"的按钮）；
再由你用 TalkBack 走一遍主流程。**B** 等你用 TalkBack 发现问题再改：问题会一次来很多。

## 4E 工程化

### 1. 界面冒烟测试（推荐 A）

| 备选                                                                                                                            | 取舍                                            |
| ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| **A Playwright，只装 Chromium（约 150 MB 下载）；写 5 条：新建、编辑、删除和撤销、备份导出再导入、生成分享图；AI 接口用假数据** | 业界常用，跑在真浏览器里                        |
| B Vitest 的浏览器模式                                                                                                           | 同样要下载浏览器，多页面流程支持不如 Playwright |
| C 不做，靠手测                                                                                                                  | 每次改完都要手动点一遍                          |

### 2. 提示词样例集（推荐 A）

| 备选                                                                                                                                                              | 取舍                                   |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| **A 你从备份里挑 10–20 条真实记录（照片 + 原话），放在不进 git 的目录；脚本批量调本地服务端，生成对比网页：新旧提示词的结果并排，附字数和"添油加醋"形容词的个数** | 人看最准；照片是隐私，不进仓库         |
| B 再让模型给结果打分                                                                                                                                              | 便宜，但"模型评模型"不可靠，只能当参考 |
| C 只看字数这类硬指标                                                                                                                                              | 看不出写得像不像你                     |

### 3. 自动检查（推荐 A）

**A** 先加一个 `npm run check`（类型检查、代码检查、测试、格式），本地随时跑；建好远程仓库后再加 GitHub Actions，
构建时缓存那 50 MB 的资源。**B** 加提交前钩子（husky）：每次提交都要等检查跑完，提交本来就由我在检查后做，用处不大。

## 只能你做的

- 阿里云控制台设费用预警。
- 建 GitHub 远程仓库（要不要公开、仓库名由你定），之后推送要你同意。
- 找一个不翻墙的网络打开网页版，看主页、AI 整理、地图、语义搜索能不能用；打不开按 0007 的兜底方案买域名。
- 用安卓的 TalkBack 走一遍主流程。
- 挑提示词样例。
