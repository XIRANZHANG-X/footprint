## 3. 服务端限流（0015 的 A：Workers 自带的限流绑定）

| 绑定               | 管哪些接口                                   | 每个"IP + 接口"的上限 |
| ------------------ | -------------------------------------------- | --------------------- |
| `AI_RATE_LIMIT`    | 花百炼额度的：整理、转写、偏好提炼、出行总结 | 每 60 秒 20 次        |
| `LIGHT_RATE_LIMIT` | 不花钱的：口令验证、查地名、按地名搜地点     | 每 60 秒 30 次        |

- 配置在 `wrangler.jsonc` 的 `ratelimits`，代码是 `server/app.ts` 的 `rateLimit`。
- 超限返回 429、`Retry-After: 60` 和"请求太频繁了，过一分钟再试"。App 原样显示服务端给的错误文字，不用改前端。
- **限流放在口令检查前面**：猜错口令的请求也计数，顺便挡住反复猜口令。0015 只说了挡刷量，这一点是实现时加的。
- 计数的 key 是 `CF-Connecting-IP` 加接口路径，各接口分开算：
  - 整理一条记录要先查地名再整理，两个接口互不占额度；
  - 正常使用一分钟也就几次，碰不到上限。
- 本机 Node（`npm run dev`）没有这两个绑定，不限流。线上如果绑定没配上，也是不限流（放行），不会因此整个服务不能用。
- 局限（0015 已说明）：
  - Cloudflare 的计数是近似的，各机房分开算。挡得住口令泄露后的刷量，挡不住慢慢地用。
  - 最后一道防线是阿里云控制台的费用预警，要用户自己设。

| 备选                                 | 结论 / 原因                                                   |
| ------------------------------------ | ------------------------------------------------------------- |
| **A Workers 限流绑定**               | **选定**。免费，几十行代码，本地 `wrangler dev` 也能模拟      |
| B Cloudflare 防火墙（WAF）的限流规则 | 只能用在自己的域名上，`*.workers.dev` 用不了                  |
| C KV 或 Durable Object 记每天的次数  | 能做真正的每日上限，但工程量大；KV 免费额度每天只能写 1000 次 |

## 验证

- 新增 3 个服务端测试，用假的限流绑定验证了这几件事：
  - 按"IP + 接口"计数；
  - 先计数、再查口令；
  - 超限返回 429 和 `Retry-After`；
  - 花钱的接口用 AI 那个绑定；
  - 本机没有绑定时不限流。
- 本地 `wrangler dev` 实测（只打不花钱的 `/api/auth/check`，没有调用百炼）：
  - 绑定被识别为"20 requests/60s""30 requests/60s"；
  - 连续 33 次请求，前 30 次 401（没带口令），后 3 次 429；
  - 同一时间 `/api/geocode` 不受影响。
- 用户同意后部署（2026-11-24，版本 28e63062），线上实测，只打不花钱的 `/api/auth/check`：
  - 同一个连接连发 60 次：前 25 次 401，之后全部 429，提示文字正确。
  - **每次新开连接**连发，一分钟内 100 多次都没被拦。
    Cloudflare 文档说每台机器用本地计数、后台再同步，请求分散到不同机器时会明显超过上限。
  - 所以这层限流挡得住普通的重复刷，挡不住刻意每次换连接的人。真正兜底的是：
    - 口令（猜中的可能性可以忽略）；
    - 阿里云费用预警。
  - 要严格上限得改用 Durable Object（0015 的 C），现在不值得。
