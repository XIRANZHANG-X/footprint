## 补充：照片线索查表，借自 geo-sleuth（2026-11-23 定）

用户看到 [geo-sleuth](https://github.com/Oldcircle/geo-sleuth)（MIT 协议），问这个 App 能不能用它来定位。

### 它是什么

一个给编程 agent（Claude Code、Codex 等）用的 Agent Skill：一份操作说明（SKILL.md）加二十多个 Python 脚本，
agent 边读说明边在电脑上跑脚本。运行要 Python、uv、Chrome（以图搜图），首次要下载约 2.4 GB 的图像模型，
数据来自 OpenStreetMap、高程、卫星图、百度全景和 Google 街景。README 里的案例每张照片 32–72 分钟、
87–154 次工具调用，用的是 Claude Opus 级别的模型。它解决的是"一张来历不明、没有定位信息的照片在哪拍的"。

### 决定：不接入，只借查表数据和"模型读字、程序查表"的思路（选定 A）

| 备选                                                                               | 结论 / 原因                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A 不接入；借它的中国车牌前缀、固话区号、行政区划表，做"照片线索指向的城市"候选** | **选定**。成本小，补上"AI 猜测"不可靠的问题，不多上传任何东西                                                                                                                                                                                                                                                               |
| B 不接入 App；用户需要时自己在电脑上用这个 skill 跑一次老照片，结果手动填回        | 不用写代码，可以随时自己用，和 A 不冲突                                                                                                                                                                                                                                                                                     |
| C 另租服务器，自己写 agent 驱动它，做成"深度定位"按钮                              | 不选：① 手机和 Cloudflare Worker 都跑不了 Python 和 Chrome；② 它按 Opus 级模型写和测，换 qwen 能否走通不确定，每张照片几十上百次调用很贵；③ 要把照片发给百度、Yandex 以图搜图和街景，违背 0002 的隐私原则；④ 手账用户自己去过、知道是哪，缺的只是地名转坐标，这靠第五档"换高德"解决；⑤ 开源后等于提供了定位陌生人照片的工具 |

### 怎么做（排在 3C 里，和"所在城市"一起做）

- 整理照片时，让模型在返回的结构里顺带列出**照片里读到的**电话号码和车牌（只抄字，不判断城市）。
- 前端用查表得到城市：区号取最长前缀匹配，车牌取"省份简称 + 字母"；一个键对应多个地方时全部列出，不挑一个。
- 结果在"补地点"里显示成单独一组，例如"照片里的电话区号指向：杭州"，点了以后在这个城市范围内查地名。
  它和"AI 猜测"一样只是候选，不自动写进记录。
- 道理（来自 geo-sleuth）：读出来的字是有据可查的，模型凭印象猜城市不是。

### 数据和协议

| 文件（geo-sleuth `regions/cn/data/`） | 内容                     | 条数  | 来源和协议                                      |
| ------------------------------------- | ------------------------ | ----- | ----------------------------------------------- |
| `plates.json`                         | 车牌前缀 → 省、市        | 501   | 整理自中文维基百科，CC BY-SA 4.0                |
| `area_codes.json`                     | 固话区号 → 省、市        | 349   | 整理自中文维基百科，CC BY-SA 4.0                |

## 实现记录（2026-11-23，3A–3E 一次做完）

### 和上面方案不一样的地方

1. **中国的"城市"不是由边界数据算出来的。** geoBoundaries 的中国 ADM2 实际是 2391 个区县，名字只有拼音，也没有所属地级市，
   得不出"杭州市"。改为：省级用 Natural Earth 判断；地级市取地名查询（Nominatim）返回的城市字段，
   服务端 `/api/geocode` 新增 `city`；旧记录从已存的地名文字里拆，只认行政区划表（`public/data/cn/admin.json`）里真有的名字；
   都拿不到时退回省级（直辖市本来就是省级）。国外按省、州一级；香港、澳门、新加坡等直接用地区名。
2. **地图点亮的粒度**：中国按区县点亮（geoBoundaries 区县边界），其他地方按省、州。缩小到全国时区县只有几个像素，
   所以每个点亮的区域另画一个小圆点。
3. **离线底图不是瓦片，而是打包的省州边界线。** OSM 的瓦片使用规定不允许批量下载打包；
   改为在线瓦片加载失败时，在瓦片下面画出 Natural Earth 的省州轮廓。街道级仍然要联网。
4. **向量不是在保存时算，而是第一次用搜索时在后台补齐**，之后每次搜索只算新增和改过的记录。
   这样不用搜索的人不会每次打开都加载 24 MB 的模型。
5. **九宫格两种都做了**（用户在开工前选定）：拼成一张的"九宫格"版式，和导出多张图的"朋友圈多图"版式。

### 实现要点

- 体积大的资源不进 git，由 `scripts/prepare_assets.mjs` 准备，`npm run dev` / `build` 之前自动运行（`npm run assets`）：
  `public/models`（bge-small-zh-v1.5 量化版 24 MB）、`public/ort`（onnxruntime 只跑 CPU 的 wasm 14 MB）、
  `public/geo`（精简后的边界：全球省州 9.7 MB、中国区县 2.4 MB）。原始下载缓存在 `.cache/assets/`。
  onnxruntime 默认引用的 asyncify 版 wasm 有 26.9 MB，超过 Cloudflare 单文件 25 MB 上限，`vite.config.ts` 里构建时去掉。
- 语义搜索在 Web Worker 里跑，模型和 wasm 都从 App 自己的地址加载，不访问 Hugging Face 和 CDN。
  阈值用 5 条样例实测：意思相关的 0.37–0.55，无关的 0.2–0.35；取 ≥ 0.36 且离最好的一条不超过 0.1。
- 向量存在新表 `embeddings`（数据库 v6），可以重算，不进备份。记录上新增可选字段 `area`、`geoCity`，后台补，会进备份。
- 照片线索：`/api/describe` 的结果多了 `clues`（电话、车牌，模型只抄字）；"补地点"里查表显示城市，点了把城市名加在地名前面去查。
- 出行总结：新接口 `POST /api/summarize`，只发每条记录的日期、标题、地名、正文；结果存在设置表 `trip:<出行第一条记录的 id>`，
  跟着备份走。出行被拆分或合并后第一条记录变了，原来的总结就找不到了（数据还在设置表里）。
- 分享：五种版式，自动推荐 + 小预览切换；长图按"一行字、一张照片"为单位分页，每页不超过 8000 像素。
  一次多张图时，App 里逐张存相册再一起分享，网页版逐张下载。
- 字体换成完整版（695 KB），`scripts/subset_font.py` 删除（见 0010 的更新）。

### 验证情况

- 浏览器里（假数据，AI 和地名接口用桩）验证过：搜索和筛选、语义搜索（"吃辣的"找到写着"很辣"的拉面）、区域和城市后台补齐、
  "第几次来"和"第一次来某城"、首页统计、照片线索城市和带城市的地名查询、地图点亮和放大后的地点标记、五种分享版式、
  出行总结和长图、回顾页、一年前的今天；320 像素宽没有横向滚动。生产构建里的 Worker 能离线加载模型。
- 没验证：手机上的速度（模型第一次加载、十几 MB 边界数据的解析）、安卓 WebView 里 Worker 和 wasm 能不能跑、
  真实模型抄电话车牌和写出行总结的效果、Nominatim 返回的城市字段在国内准不准。
- 服务端改了（`/api/summarize`、describe 的 `clues`、geocode 的 `city`），线上要重新部署才生效。
